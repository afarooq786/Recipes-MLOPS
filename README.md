# Recipe Recommender — MLOps Pipeline

An open-source recipe recommendation system that predicts whether a recipe will be
positively rated (rating ≥ 4), built as a full MLOps pipeline: data ingestion → validation →
versioning → feature engineering → training → tracking → deployment → monitoring.

This README currently documents the **data ingestion, validation, splitting, versioning,
preprocessing, feature engineering, baseline model, and evaluation stages (steps 1–8)**.
Sections for training/tracking, deployment, and monitoring will be filled in by the rest of
the team as those pieces land — see [What's Next](#whats-next) below.

## Setup

1. **Clone the repo** and create a virtual environment:
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. **Kaggle credentials** (only needed to run `data/ingest.py` yourself — not needed if you're
   just pulling already-versioned data via DVC):
   - Go to kaggle.com → Settings → API Tokens → Generate.
   - `export KAGGLE_API_TOKEN=<your token>`

3. **GCP access** (needed for `dvc pull` / `dvc push`):
   - Ask Amir to add your Google account under IAM on the `recipe-mlops` GCP project.
   - Install the [Google Cloud CLI](https://cloud.google.com/sdk/docs/install).
   - `gcloud auth application-default login` (sign in with the account that was added)
   - `gcloud config set project recipe-mlops`

   See `docs/Recipe_MLOps_Data_Infrastructure_Handoff.pdf` for the full walkthrough.

## Reproducing the Data Pipeline Locally

Once setup is done, the ingestion → validation → split pipeline runs with one command:

```bash
dvc repro
```

This runs, in order:

| Step | Stage | Script | What it does |
|------|-------|--------|---------------|
| 1 | `ingest` | `data/ingest.py` | Downloads `recipes.csv` and `test_recipes.csv` from Kaggle into `data/raw/`. Idempotent — skips re-downloading if the files already exist (use `--force` to override). |
| 2 | `validate` | `data/validate.py` | Validates `recipes.csv` against a defined schema (required columns, dtypes, null rules, allowed ranges). **Fails the pipeline** (non-zero exit) on critical issues — missing columns, out-of-range ratings, invalid servings, etc. Writes `data/validation_report.{json,md}`. `test_recipes.csv` is checked too but reported as warnings only, since it's a separate holdout set (see below) and doesn't gate this pipeline. |
| 3 | `split` | `data/split.py` | Refuses to run unless the validation report shows a pass. Builds the binary label (`rating >= 4`), **deduplicates** recipes that appear as identical rows more than once in the raw data (see [Known Data Notes](#known-data-notes)), then produces a reproducible, seeded (`--seed 42`), stratified 70/15/15 train/val/test split. The test split is written separately and is meant to stay untouched by model selection/tuning. |
| 4 | *(all of the above)* | `dvc.yaml` / `dvc.lock` | DVC tracks every stage's inputs and outputs by hash. `dvc repro` only re-runs a stage if its code or dependencies changed — everything else is a fast no-op. |

To pull the exact versioned data instead of regenerating it locally:

```bash
dvc pull
```

To push a newly generated version to the shared GCS remote (`gs://recipe-mlops-dvc`) after
changing anything upstream:

```bash
dvc push
```

Each script can also be run and configured individually — run `python data/<script>.py --help`
for options (custom seed, split fractions, output paths, etc).

## Preprocessing, Features, Baseline & Evaluation

These stages aren't wired into `dvc.yaml` yet — run them manually after `dvc repro` / `dvc pull`
has produced `data/processed/splits/`:

```bash
python preprocessing/preprocess.py
python features/build_features.py
python models/baseline.py --eval-split val
```

| Step | Stage | Script | What it does |
|------|-------|--------|---------------|
| 5 | `preprocess` | `preprocessing/preprocess.py` | Reads `data/processed/splits/{train,val,test}.csv`, normalizes text fields, parses `ingredients` into a cleaned list (`ingredients_parsed`, `ingredient_count`), converts `prep_time`/`cook_time`/`total_time` strings into numeric `*_minutes` columns, drops rows missing required fields (`recipe_name`, `ingredients`, `directions`), and does a residual dedupe. Exposes `preprocess_dataframe()` for reuse. Writes `data/processed/clean/{train,val,test}.csv`. |
| 6 | `build_features` | `features/build_features.py` | Builds nutritional (flattens the `nutrition` JSON blob), ingredient (counts, diversity, protein-type flags), cooking-time (buckets, prep-to-cook ratio), dietary-preference (heuristic vegetarian/vegan/gluten-free flags — keyword-based, not authoritative), and recipe-popularity (cuisine-relative rating z-score, **fit on train only** to avoid leakage) features. `--synthetic-user-features` optionally attaches placeholder `synth_*` user-interaction columns, since this dataset has no real per-user interaction log (see [Known Data Notes](#known-data-notes)) — these are clearly labeled and logged as synthetic, not real behavior. Writes `data/processed/features/{train,val,test}.csv` + `feature_manifest.json`. |
| 7 | `baseline` | `models/baseline.py` | The required non-ML baseline: ranks/scores recipes by their cuisine's train-set mean rating (`PopularityBaseline`), falling back to the global mean for cuisines unseen in train. Writes the fitted lookup table, predictions, and calls into `evaluation/metrics.py` to score itself. |
| 8 | `evaluate` | `evaluation/metrics.py` | Reusable `evaluate()` function — ROC-AUC (returns `None` instead of raising if only one class is present) and Precision@5, computed both overall and grouped (defaults to `cuisine_path`, swappable via `--group-col` once real per-user data exists). Saves results as JSON plus an ROC curve and Precision@k bar plot (PNG). Meant to be imported by every model's eval step (baseline, Logistic Regression, XGBoost, etc.) so metrics are reported consistently. |

**Note:** built and tested against synthetic data in a sandboxed environment without Kaggle/GCS
network access — worth a sanity check against the real `recipes.csv` (especially the `nutrition`
JSON field names) after your first `dvc pull`.

## Known Data Notes

A few things worth knowing before building on top of this data:

- **`recipes.csv` (1,090 rows) is the only file used for training/validation/testing splits.**
  It's an Allrecipes.com-sourced recipe dataset (Kaggle:
  `thedevastator/better-recipes-for-a-better-life`) with a single aggregate `rating` per recipe
  — there is no separate per-user interaction dataset, so the classification task is "will this
  recipe be rated ≥ 4," not a personalized per-user prediction, unless synthetic user profiles
  are introduced later in feature engineering.
- **`test_recipes.csv` (59 rows) is a separate, differently-shaped holdout set** (capitalized
  columns, no rating, structured ingredient records) and is *not* part of the train/val/test
  split here — it looks like the intended "clean test dataset" for the later production
  validation / drift-simulation stage of the pipeline.
- **129 duplicate rows** were found in the raw `recipes.csv` — identical recipes (same name,
  ingredients, rating, everything) appearing more than once, differing only in a meaningless
  source row index. `split.py` dedupes these before splitting so the same recipe can't leak
  across train/val/test.
- **Class imbalance:** after dedup, about 94–95% of recipes have `rating >= 4` (positive class)
  across every split. Worth flagging for whoever's training models — plain accuracy will look
  great and mean very little; ROC-AUC and Precision@5 (the metrics in the proposal) are a much
  better read on this, and class weighting is worth considering during training.
- **No real per-user interaction data.** `features/build_features.py`'s user-interaction features
  are synthetic placeholders only (opt-in via `--synthetic-user-features`) until a real
  interaction log exists upstream — see the table above.
